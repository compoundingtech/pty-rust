# 0002 — ANSI serialization bytes differ from Node but restore the same screen

**Status:** accepted

**Node behavior.** `pty peek` (ANSI), the ATTACH `SCREEN` payload, and the
testkit's `Screenshot.ansi` are produced by `@xterm/addon-serialize` 0.14.0
(`node_modules/@xterm/addon-serialize/src/SerializeAddon.ts`): SGR diffs per
cell run, empty-cell runs as `ESC[nX ESC[nC`, rows separated by `\r\n` unless
wrapped, a relative cursor move at the end, then the addon's own mode string
and, if the alternate buffer is active, `ESC[?1049h ESC[H` + alt content.
Node's daemon prepends `getModePrefix()` (`src/server.ts:1065-1082`).

**Rust behavior.** The same prefix, generated byte for byte from the actor's
tracked flags (`crates/pty-terminal/src/serialize.rs`, `mode_prefix`), followed
by libghostty's `Format::Vt` (soft-wrapped rows unwrapped, modes and kitty
keyboard state) plus three additions the serializer makes itself, in this
order: `\r\n` padding for the trailing blank rows libghostty omits (only when
scrollback exists, so the client's buffer has as many rows as the daemon's and
the viewport lines up), `CUP` + `SGR bg` + `ECH n` for every text-less row of
the active area that carries a background (libghostty drops such rows; xterm
keeps them the same way), and an absolute `CUP` for the cursor. The body's
bytes differ from xterm's: `ESC[=flags;1u` for kitty flags, its own mode list
order, background-only cells on rows *with* text emitted as styled spaces, and
no primary-buffer content when the alternate buffer is active.

**Why.** Reproducing xterm's serializer would mean a second serializer that
walks libghostty's grid and re-implements xterm's style-diff and ECH/CUF
heuristics; every consumer of the payload is a terminal that parses it, and
what matters is the picture it restores. The prefix is kept exact because
tests pin its position (`ESC[?1049h` at byte 0) and clients grep it.

**Client effect.** A client feeding either payload to a terminal ends up with
the same picture: cells, colours, attributes, cursor row, modes. Known
residual differences: (1) on a row that has text, cells erased with a
background come back as *written* spaces with that background, so the plain
text of a screen read back from the client side (a reattached testkit
session, not the daemon's own `peek`) carries trailing spaces on such rows;
(2) background-only rows that have already scrolled into history are not
restored (xterm restores them); (3) a cursor pending a wrap after the last
column lands on the last column (as with xterm's addon). Code that greps the
raw payload for xterm's exact byte patterns will not find them; code that
greps for SGR parameters (`48;2;71;76;86`) still does.

**Test.** `crates/pty-terminal/tests/replay.rs` (`round_trip`): every
ratatui-style fixture is serialized in one actor and parsed by a second one,
and the two are compared cell by cell (text, fg/bg including palette index,
bold/dim/italic/underline/inverse/strikethrough), plus wrapped flags, buffer
shape (`base_y`, `buffer_length`), cursor, and the tracked modes; the plain
text is compared right-trimmed because of residual (1).
`kitty_push_and_scrollback_survive_replay` covers the row padding,
`full_screen_el_background_is_kept_on_every_row` the background fix-ups.
Node's raw-byte expectations from `tests/ratatui-compat.test.ts` are kept
where they are parameter-level (`ansiContainsSGR`). Oracle for xterm's
handling of background-only rows: `pty 0.12.0+500eab2`, `pty peek` of a
session that ran `SGR bg` + `EL` on five rows with text on one — every row
came back as `ESC[48;2;…m ESC[80X`.

**Migration.** None for terminals. Tools that parse the payload should parse
it with a VT parser (libghostty, xterm) rather than pattern-match bytes.
